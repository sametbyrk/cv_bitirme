# 04 — Endpoint, UI and Security (v2)

## Current API contract

`POST /api/v1/ai/match` accepts authenticated JSON using the existing camelCase contract: `jobDescription`, exactly one of `resumeId` (saved resume) or `currentResume` (unsaved draft), and optional `targetLanguage`. Saved resumes are queried by both ID and authenticated owner; another user's resume returns 404. Draft photos are removed before analysis.

Successful results are persisted in `public.ats_match_history` and can be listed with `GET /api/v1/ai/match/history` or deleted with `DELETE /api/v1/ai/match/history/{id}`. Every read/delete is scoped to the authenticated user. The record stores the job description and complete explainable score response, including short CV evidence excerpts (up to 25 words each), but not a resume snapshot. Records expire after 90 days and are capped at the latest 50 per account, whichever limit is reached first. Backend history reads/writes prune expired rows; the authenticated daily Vercel cron also performs scheduled cleanup. The cron requires `CRON_SECRET`. Deleting a saved resume cascades to its linked ATS history; draft analyses remain linked only to the user's account. The account-history foreign key also cascades if a `User` row is actually deleted; this repository currently has no user-facing account-deletion flow. Apply `backend/sql/ats_match_history.sql` before deploying these endpoints. Browser/Supabase client roles receive no table permissions; access is through the backend database role.

`jobDescription` is limited to 20,000 raw characters. Empty or whitespace-only input returns 400 (`JOB_EMPTY`); over-limit text returns 413 (`JOB_TOO_LONG`); non-empty text shorter than 30 visible characters returns 422 (`JOB_TOO_SHORT`); CV JSON over 150 KiB returns 422 (`CV_TOO_LARGE`); CVs without comparable text return 422 (`CV_NO_TEXT`). The required-skill errors are `NO_REQUIRED_SKILLS` and `REQUIRED_UNVERIFIED`. The independent 256 KiB raw AI request-body middleware returns 413 (`REQUEST_BODY_TOO_LARGE`). Authentication returns 401; owner mismatch/not found returns 404; invalid model output returns 502; provider errors and phase/overall timeout return 503; abuse limit and product quota return 429 with distinct `RATE_LIMITED` and `AI_QUOTA_EXCEEDED` codes. The limiter forwards `Retry-After` through the Next.js proxy.

## Quota and abuse limiting

All AI operations share the product quota. Free accounts receive five uses per rolling month, starting with the first successful AI operation. Premium accounts receive 50 successful uses per rolling 24 hours, counted from consumed reservations; this is separate from ATS abuse limits. A short PostgreSQL reservation is created before provider work, finalized as consumed only on success, and released on failure/timeout. The same reservation utility covers field rewriting, Auto-Tailor, and ATS matching. AI generation requests time out after 20 seconds, shorter than the three-minute reservation lease. Apply `backend/sql/ai_usage_reservations.sql` before deploying; until then quota access fails closed with 503. The existing `rate_limit_bucket` table from `frontend/prisma/rate_limit.sql` must also exist for ATS abuse limiting. Expired reservations are ignored in quota counts and marked released on later reservations. The separate abuse limiter uses atomic PostgreSQL buckets, 10 requests/minute and 100/day per account and client IP; it trusts `X-Forwarded-For` only when `TRUSTED_PROXY_HOPS` is configured, returns `Retry-After`, and fails closed with 503 when unavailable. The daily abuse ceiling is separate from free/premium product quotas.

## Timeouts, privacy and cache

Extraction budget: 10 seconds; embedding budget: 8 seconds; overall request budget: 20 seconds. Timeouts return phase-specific or `ATS_TOTAL_TIMEOUT` 503 codes. Never log raw job or resume text; log only opaque identifiers, hashes, lengths, and error categories. Existing caches are bounded in-process caches: extracted skills use a job-text hash and 24-hour TTL; evidence embeddings use the evidence-unit hash. There is no shared score-result cache; user-requested analysis history is stored separately in the database.

Prompt-injection checks are heuristic risk reduction, not a guarantee. Provider system instructions must treat supplied content as untrusted data. The request body remains capped at 256 KiB.

## UI behavior

The editor shows score, confidence, rule/hybrid coverage, exact evidence, semantic supporting evidence, and missing skills sorted by impact. It has loading, error, empty, and success states; errors are localized for Turkish, English, German, Spanish, and French. Users can reopen and delete their last 50 successful analyses. The UI discloses that the job-description text and score are saved; ATS results never auto-edit the CV. Auto-Tailor remains a separate user-reviewed action.

The response's `excludedSkillCount` is shown when nonzero with a localized explanation. It counts malformed, duplicate, capped, or evidence-unverified extracted rows; none of those rows are scored.

## Manual/evaluation gates (not claimed complete by this plan)

Unit/mock tests cover reservation success and failure handling, but they do not prove PostgreSQL locking under concurrent requests. The opt-in integration test `backend/tests/test_ai_quota_concurrency.py` uses six parallel reservations against one free test user and expects exactly five reservations plus one `429 AI_QUOTA_EXCEEDED`. Run it only against a dedicated, migrated test database by setting `ATS_CONCURRENCY_TEST_DATABASE_URL`; it creates and removes a synthetic user and its reservation rows. The test does not fall back to the application's normal `DATABASE_URL` and has not been run unless explicitly reported.

Other gates: test auth, ownership 404, each validation/error code, 413 raw body handling, rate-limit Retry-After/fail-closed behavior, reservation expiry, phase timeouts, prompt-injection attempts, and all UI states. Do not claim these gates pass until actually run. Research/evaluation data must be anonymized before sharing.

Before using AI features with real CV data, verify that the configured Gemini project is on Paid Services. The repository cannot inspect Google Cloud billing status. Under Google's published service terms, Unpaid Services may use submitted prompts and responses to improve products; privacy notice text alone does not change the project's service tier. If the project remains on Free Tier, do not send real users' CVs or other personal/sensitive data until an appropriate data-processing setup is in place. Separately determine and implement the applicable KVKK processing basis and cross-border transfer safeguard before offering the feature to real users. The current privacy page discloses the service-tier distinction and states that these operator-side legal steps remain outstanding; it is not a substitute for completing them.
